# 自动待避：四项界面、连续快车及多入口修复

## 交付范围

以当前 `px-patch` 工作区继续开发，保留此前未提交修改，没有还原旧源码、改写历史或上传 GitHub。参照截图及本机 `OpenTTD-pxp-20261022-181625-win64`（周四约 18:17 的包）核对名称；其四个中文名称与本次一致。

自动待避的新增／类型菜单只提供以下四项。原生寻路限制的其他普通功能继续保留。

| 选项 | 功能 |
| --- | --- |
| 接近检测 | 使用同一路签登记列车，保留路径预留／车头／车尾三种登记时机、速度差及速度上限设置 |
| 正线控制 | 在有合法可用侧线且确认需要让行时，使用原有限制和 PBS 安排待避 |
| 待避股道出口 | 识别普通待避线或站台，认领停车段；需要让行时执行等待，出清后放行 |
| 车尾清除点 | 由实际车尾经过释放登记及相应目标关系 |

隐藏旧版股道入口和额外七个自动待避条件的新增选项；保留它们的编号、解释器和显示映射，已有存档里的指令仍能显示并执行。普通模式和开启高级选项时均实测四个自动待避动作、零个额外待避条件，七种旧条件名称均可解析。见 `validation/ui-native.log`。

## 已确认根因与最小修改

1. **后续快车认领缺失。** `RememberYieldTargets` 原先仅在成功提交股道／出口预留时记录目标。停车车辆没有前方预留时，`RefreshAutoYieldMainReservation` 提前返回，新来的快车没有稳定的补充机会。`MustWait` 还可能把它当成新出线请求，用远车时间例外放行。
2. **串联正线控制被误作独立道路。** `MergeClearanceDistance` 遇到第二个 Main 就截断；`RouteToRole` 也无法穿过前面的 Main 查找指定后续 Main。相反，平行逃生证明可能重新经过本应避开的 Main。
3. **分流前存在空侧线却拒绝入线。** 多出口时，从车头到目标的全局预测可能消耗在无关分支上。即使候选侧线本身能通往本车目的地，也被“出口未知”整体排除。

对应修改集中于 `src/tracerestrict_overtaking.cpp`：

- `YieldWaitInProgress` 使用已保存的股道目标及原生 PBS 停车状态确认等待，不添加本机状态开关。
- `AutoYieldGameTick` 在预留检查之前，有界补充停车列车的新目标；`RememberYieldTargets` 对确认冲突的后续快车逐辆保存认领，公平扫描顺序只取决于游戏 tick 和车辆 ID。
- `MustWait` 对已经处于有效等待过程的列车保留连续待避。未知路线不建立新强制关系，也不单凭查询未知清除已有关系。
- `RouteToRole` 和 `MergeClearanceDistance` 统一处理串联控制，平行逃生证明不得返回受控 Main；实际 Clear 仍是边界。
- `FreeLane` 在必要时从候选股道出口证明它能到达本车当前目标，并匹配其第一出清点，避免把入口前无关岔路当作侧线不可达。`GetGoalClearanceHint` 的临时缓存增加起点及方向键。

`src/tracerestrict_gui.cpp` 只改变额外选项的显示标志。相关单元测试和 `regression/automatic_yield` 增加真实行驶回归；没有修改原生寻路器或使用惩罚值模拟停车。

## 冲突识别与等待生命周期

延续已有的有向轨道、列车实际路径／车体和共同冲突分类。先确认共享、交叉或独立资源，再比较速度和既有客货优先规则；不是把同一路签或整个车站当成一个互斥区。

已认领股道保存待避目标的车辆 ID。第一辆快车出清只释放自己的关系；后续快车尚有实际冲突时，慢车继续停车。快车明确改道到独立路线、被删除或取消登记时重新评估对应目标；临时查不到路径不等于全部放行。快车经过车站或车头离区本身也不是清空所有目标的依据。

没有替代原生占用、信号及 PBS 的安全判定，没有强抢已经提交的出线预留。保留站台停站、普通侧线、混合股道、满线安全腾位、换向及无路签车辆占用检查。既有满线算法本轮未重写，其远快车允许安全腾位、近快车禁止提前腾位的真实运行回归仍通过。

## 先失败、后修复的证据

- 新的“等待期间加入后续快车”单元测试在本轮修改前产生 3 个失败断言：后续目标未保存、第一目标离开后等待解除。修复后通过。
- 把修改前的生产待避实现与同一原生行驶驱动链接，连续快车地图在 tick 1859 以退出码 82 失败：第一车已清空、后两车仍未清空，慢车却启动。这是真实车辆运动，不是仅调用决策函数。
- 强化不同出口测试，要求慢车先进入侧线让开分流前共用路径，再在路线独立后继续。旧实现没有进入侧线，因缺少该阶段失败；修复后 `CONFLICT 753 → ENTER 1006`，之后无错误停车。
- 没有删除原有安全断言。串联信号单测修正为“仍有跟随冲突”，并额外检查已过最后侧线入口的列车不会被强制停在无可达侧线的 Main。

## 原问题存档：27／102 与永城

固定输入为用户 2026-10-24 17:07:51 的存档副本，9,775,508 字节，SHA256：

`bcb20d4bb29790e66e45838961c9fc4413b87cc472e5f929ee1ec7055d2d4115`

原文件没有改写。公司 1 的 27 号内部 ID 21118，102 号内部 ID 31442。输入开始时，27 已在德州下行侧线出口外行驶，无法从这一时刻回放之前为何启动。

**“27 到永城无法进入侧线”在这份副本的本次行程未复现，修改前基线也会进入并等待 102。** 本轮不能将该历史事件声称为已逐步复现并修复。

最终核心实现重放 10,000 tick：27 进入永城下行路签 333 的侧线 `(614,3749)`，tick 2816 的采样中速度为零，股道认领持有目标 31442；持续停车采样至 3712。102 已出清登记后，27 于 3776 采样恢复移动，随后释放认领。上述为每 64 tick 采样，不能当作精确的进入／出清时刻。

同时读取了地图上 15 个自动待避区域的配置并检查车辆位置索引及路签反向索引，结束记录 `RESULT ticks=10001 invalid=0`。这证明受测时段的检查结果，不等于所有区域、所有交通组合均已触发。随州西北原生限制示例作为入口登记、出口等待、车尾释放的工作模式对照，没有复制固定坐标或无效路签引用。
