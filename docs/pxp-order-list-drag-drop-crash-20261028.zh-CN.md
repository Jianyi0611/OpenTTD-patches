# 独立调度表点击松开崩溃修复

## 根因与证据

对应用户提供的 `crash-20261027T134301Z.log/.sav/.png`，原程序版本 `pxp-2611.1-p2-7-g080f9d580`。使用当时正式程序 SHA256 `65580483092d70d6ec0755bd138e3c1bb685fdebf76bf7ce34f13c3f174ef917` 校验后，崩溃指令的24字节在文件中唯一匹配。文件偏移 `0x76038D`、代码RVA `0x760F8D` 推出实际加载基址 `0x7FF67F5F0000`；对应 `OrdersWindow::OnDragDrop + 0x38D`。

该指令先读取窗口的 `vehicle`，再读取 `Vehicle::orders` 的 `0x220` 偏移。报告中 `RAX=0`，故障地址也恰为 `0x220`。COFF函数符号及反汇编与080f源码 `src/order_gui.cpp:6986–6987` 相符。程序中没有可供此函数精确行号使用的DWARF信息，本结论来自匹配程序字节、函数符号及对应源码分支，不冒充已获得完整调试行号。

独立调度表编辑器合法地没有关联车辆。选中调令后在同一行松开鼠标，拖放处理却调用了 `this->vehicle->GetNumOrders()`，随后还调用 `this->vehicle->GetOrder()`。这使普通点击也可能崩溃，和该调令是否为车站、路点或文字无关。

在用户的原始崩溃存档中，实际打开8116号独立调度表，经真实 `OnClick` 后调用真实 `OnDragDrop`，复现 `C0000005`、`RAX=0`、访问 `0x220`，指令字节与原报告相同。输入存档复制前后哈希均未变化。证据在工作区 `tools/yield-early-route-20261027/crash-investigation/ui-order-drop/player-before.log`。

## 最小修复

只修改 `OrdersWindow::OnDragDrop` 两处调用，改用窗口已有的 `NumOrders()` 和 `OrderAt()`。两者已经统一支持车辆调令和独立调度表；保留原有同位置点击文字标记的编辑功能，不直接跳过独立调度表交互。

不修改列车状态、寻路、PBS、连挂解挂或存档格式，不需要调整问题存档中的线路或调度内容。

## 可重复回归
