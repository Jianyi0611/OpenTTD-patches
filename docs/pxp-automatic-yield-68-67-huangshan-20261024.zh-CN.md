# 荒山下行：68 号有空位却不让 67 号修复

2026-10-24，本地 `px-patch`。使用用户当天 16:31:29 更新的 `慢车无法等待.sav` 副本，原件未修改。输入 9,789,080 字节，SHA256 `73510286b16d6191c00fa096b9440a53d4f99e2037726d9c438683cf94cccf56`。

## 已复现的故障

公司 ID 1 的 68 号（内部 ID 31445）最高速度 120，67 号（内部 ID 28143）最高速度 160。两车登记在“荒山下行”。68 号长 214 游戏长度单位，两条空闲侧线的停车长度分别为 304、312，足以容纳整列及尾部余量。

修复前，从原存档重放：68 号沿正线驶过，没有进入空闲侧线停车。该故障已真实复现，区别于此前未能重现的吕梁 47 号事件。

## 根因

1. **路径查询过早截断。**67 号到正线控制点的路线长 258 格，搜索因单次 256 节点限制被提前截断；即使一次求值的 1,024 总预算仍有余量，也被当成未知快车。独立查询修正后可证明同一个正线控制点和距离 258。
2. **把可达当成已经预留。**68 号的预留末端位于侧线分岔之前，正线和侧线都能到达。旧代码因“末端可达侧线出口”直接跳过重新选择，误以为它已预留进入侧线。
3. **额外排序否决了正确待避。**修正前两项后，仍可观察到 `needed=0 free=1 budget=0`：已经确认追越关系、也确认空位，却在对其他候选列车进行额外排序时耗尽预算，取消了正确的待避判断。这个阶段不应把查询不完整误当作“不需要待避”。

## 修改

主要文件 `src/tracerestrict_overtaking.cpp`：

- `RouteToRole` 允许使用当前求值尚余的总预算，不再叠加不合理的 256 节点截断。**总探索预算仍是 1,024，没有改成无上限搜索。**
- `GetMainApproaches` 为接近关系识别安排预算，并为后续入线检查保留余量。
- `RefreshAutoYieldMainReservation` 用列车实际连续拥有的预留路径判断侧线承诺，不把几何可达误作已预留；依原有 PBS 接口重新申请路径。
- `NeedsSiding` 只让本区域可能使用股道的车辆参与容量分配。空位足以容纳所有可能待避车辆时，不再做无必要的稀缺容量排序。
- 实际控制信号和预留重评估复用已证明的空闲入口／停车检查，避免重复检查耗尽预算。
- 已确认本车存在追越冲突且有空闲停车路径时，额外排序不完整不再直接取消待避。只有正面证明更优先的需求已用完容量，才因此拒绝；原生轨道占用、信号、车长和 PBS 检查继续生效。

没有改写 YAPF 寻路机制，没有以惩罚值模拟停车，没有增加存档字段。沿用自动待避扩展 v11；本地源码联机标识随功能修复更新，联机各端需要同一构建。
