# 合流、分流、多信号及连续快车：实施前审查

## 已确认源码问题

1. `RememberYieldTargets` 只在成功提交侧线／出口预留时记录新目标。已停车车辆没有完整前方预留时，`RefreshAutoYieldMainReservation` 会提前返回，因此等候期间新来的快车没有可靠的模拟循环补充入口。
2. `MustWait` 对未保存目标仍可使用 `CanClearBefore` 放行；这可能把已在侧线等待的车辆重新当作一次全新出线申请，在第一列通过后取消连续待避。
3. `MergeClearanceDistance` 遇到后续正线控制信号直接停止，而其他几何检查仍继续向前，串联信号和不同线路的处理不一致。`RouteToRole` 查找指定后续 Main 时，也会被前一 Main 截断。
4. 共同 Clear 是粗粒度后备证明，不应优先覆盖已经能够确认独立的实际走廊；共享预算还可能使后续候选无法获得同等的正面检查机会。

这些是源码事实，尚不能直接认定为所述历史操作的全部原因。基线重放中，27 号已从德州旧侧线启动，后续在永城确实进入侧线并等待 102 号。本轮将分别报告原事件未复现与专项测试复现，不能混为一谈。

## 统一方案与生命周期

- 入线、跟随、合流、出口等待均复用有向轨道足迹及共享冲突分类；完整独立、正面共享、未知三种状态保持区分。
- 串联控制点是同一进路上的检查点；平行正线逃生证明必须能在不再次经过当前受控 Main 的情况下离区。
- 复用每条认领股道已有的目标槽位，逐辆保存快车 ID；实际车体／路径出清、明确改道、删除或取消登记只解除相应目标。
- 模拟循环有界补充停车车辆的新目标，不在临时寻路事务中写入其他列车的状态。公平扫描顺序来自已保存游戏 tick 和车辆 ID，不使用本机时间或进程缓存。
- 已停车且仍有有效冲突时，保留连续等待；路径未知不新建强制关系，也不删除已保存有效关系。移动中的已取得合法路径车辆不被本轮新目标维护机制强行反抢。
- 保留原生 PBS、装卸、连挂、满线安全腾位及现有存档字段，不新建整站总锁。
