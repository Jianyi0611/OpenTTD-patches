# 多出口分流误等调查与修复（2026-10-29）

本次以 `px-patch` 的 `23ef6a87e78acbc2591f86887a44cb505468d7b7` 为起点，备份分支 `backup/split-dependency-20261029-022308`。证据目录为工作区 `tools/yield-split-dependency-20261029-022308`。修改未上传 GitHub。

## 已证实的根因与最小修复

1. `UpdateAutoYieldAreas` 为所有自动待避指令读取 `iter.Secondary()`，但车尾清除点 Clear 是单字指令。下一条无关指令，甚至指令数组尾后的内存，被错误当作登记方式并进入区域签名。结果是相同站场、相同存档在不同进程中偶发得到不同签名，已选路线反复被判定 `area-changed`，旧有效等待关系退回未知并持续到无关区域边界。

   确定性单元负例：在 Clear 后追加合法 penalty 指令，仅改变其与区域配置无关的高位，旧代码的区域签名发生变化，3 条断言失败（`clear-metadata-red.log`）。独立行驶反证：`replay-failure/8` 在同一等待存档的第 8 次独立进程重放中，慢车实际恢复晚于无关区域出清点，并反复记录 `area-changed`。修复后只有 Approach 才读取登记配置，其余角色使用固定的无语义值。真实区域改变仍会使计划失效。

2. `ClassifyYieldConflict` 先检查双方完整有效的实际原生选路与所有车体，再考虑原有候选出口搜索。读取已经选定的轨道序列仅消耗原有共享 footprint 额度，不再因可选拓扑查询耗尽另一额度而失去完整证据。512 共享轨道 footprint、256 单路上限及原有搜索上限没有提高。不同出口编号并不直接构成独立证明；重叠轨道、交叉及车体仍建立冲突，未知仍保留已确认的有效等待。

3. 原生重规划的起点可以在现有 PBS 前缀末端，之前的读取只找新路径，漏掉仍由本车持有的接近部分。新增只读 `GetTrainReservationPathTo`，复用原生连续预约枚举，将真正连续的已拥有前缀与新选择连接。无真实连接或缺少桥隧跨度证据时保持未知；不修改原生预约或寻路算法。

4. 旧存档可能已经持有区域路签，但尚无 `early_route_area`。仅在已有登记中能确定唯一有效多出口区域时恢复上下文；多个候选不随意挑选，手动取消路签后不能重新认领。查询不发布计划，仍需真正成功的原生 PBS 申请。

5. 在多出口混合站，已确定的当前站台入口可能位于 Main 之后。若把这段必经接近线路当作站台可绕行的正线而禁止，会绕过本应停靠的平台。`AutoYieldNativeStopNeedsApproach` 仅为本区域内、有完整原生计划的下游分支站台证明此情形；站台出口仍检查全部有效依赖。单出口、直行 Main 站台、未知计划沿用原规则。`stop-split-change` 实际运行验证了当前平台和后续目标均正确到达。

没有改动最高设计速度优先级、满线策略、连挂/解挂代码或存档字段格式，没有撤销合法 PBS 预约，没有强制列车速度、位置和停车状态。
