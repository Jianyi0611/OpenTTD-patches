# 停站后的出口方向与待避优先级：238／240 号

## 确认的问题

已读取用户 2026-10-24 18:15:19 的存档副本：9,851,268 字节，SHA256 `3ee3cb0245c2db1af23844e886d8d281ddf344d4ce29761cac23b4eed3b30411`。未改写原文件。

公司 1 的 238 号（内部 ID 37419，最高 160）正在前往 `Upper 长沙市`（站点 1088，1169,3981），下一项为车辆段 1975（1145,3982）。240 号（内部 ID 37765，最高 100）直接前往同一车辆段。两车登记在路签 143 `aaa上行`，区域有两个正线控制、两个出清点及三条股道。

源码和存档诊断共同确认：旧的 `GetSplitRouteProof` 抵达当前车站目标即把路线视作“完整”，不继续读取停站后的明确目标。因此，两条在站前分开的路线可能被 `ClassifyYieldConflict` 视为互不冲突，尽管出站后仍会汇合。同一存档 tick 0 对 240／238 的诊断由旧版 `conflict=1`（独立）变为新版 `conflict=2`（共同有向资源）。

## 修复方式

修改集中在 `src/tracerestrict_overtaking.cpp`，不改原生寻路器：

- `GetPredictionOrders` 只读当前计划，最多检查 64 项，获取一次停站之后的明确物理目标。不会执行路签操作、条件命令或切换调度计划，不调用可能消耗随机数的下一停站查询。
- 保留当前停站目标和后续目标两个阶段。`GetSplitRouteProof`、`PredictSplitTargetBranch`、`GetGoalClearanceHint` 只有在证明到达当前车站后，才预测其后方出口；不会为了去下一站跳过应停的车站。
- 装卸中，使用与实际停靠站匹配的原计划项读取下一目标。明确的站后共同路径仍可保有短暂停站优先权；不同出口按真实轨道独立性处理。
- `GetMainApproaches` 补充已经认领站台股道、但尚未经过后续正线控制的停站列车，作为需要确认后续出口的竞争者，不把它作为可以被强制腾走的装卸车辆。
- `FreeLane` 检查仅出口配置的站台时，若独占停车段已经证明包含本次停站目标，则从出口预测下一目标，不再错误要求列车回到出口后方的车站。缓存键区分该预测阶段。
- 未能唯一解析的条件跳转、连挂／解挂、执行另一个计划等保持未知。正在执行的子计划到末尾应返回父计划，预测器不会擅自循环到子计划第一站。
- 已加载车辆的后续方向未知时，只保留实际车体冲突及已有有效待避关系，不能把未知误判成路线独立、清掉有效等待。

仍保留普通短暂停站、满载等待、货类等待及长时间作业的既有区别；不会为装卸、连挂强制腾位。没有增加存档字段或网络命令，自动待避扩展仍为 v11；四项菜单不变。

## 先失败、后修复的证据

将本轮修改前的待避实现与当前测试驱动链接，四个专项单元测试产生 7 个失败断言，覆盖站后出口、装卸中出口、站台候选和未知方向的已保存等待。新实现通过，并检查实际调度、索引和随机状态未被查询改变。

额外建立原生行驶场景：112 慢车、另一个入口的 200 快车；快车先停站，之后两车汇入同一出口，有合法空闲侧线。

- 旧实现：慢车在正线 `(53,40)` 等待，未使用侧线；tick 2808 报 `FAIL station bypassed available siding`，退出码 95。原生 PBS 仍防止碰撞，但这不等于正确待避。
- 新实现：tick 1006 进入侧线，1559 在出口零速等待；快车停站结束后继续前往共同出口，2206 车尾清空，2219 慢车恢复移动，最后退出认领。

常规制动下使用更早的快车出发时刻，确保其登记在慢车预留最后入线道岔之前；该场景仍验证进入侧线、实际等待和车尾出清后恢复，不要求已经结束的装卸阶段与等待重叠。没有通过撤销既有合法预留来补救过晚登记。

## 普通线路慢车先停站、快车随后进站

同时新增玩家补充的普通场景，以及不同入口的停站汇合和停站后独立出口场景。均使用原版机车、原生站台和真实调度／时刻表命令，无车辆瞬移、速度缓存覆盖或手动放行。

同一线路、同一车站的两个站台，真实制动模式：

| 阶段 | tick |
| --- | ---: |
| 慢车开始停站作业 | 1515 |
| 快车开始停站作业 | 1629 |
| 慢车办完停站、在出口等待 | 1635 |
| 快车车尾清空相关出口 | 2030 |
| 慢车恢复移动 | 2035 |

慢车出口等待与快车实际装卸状态重叠 122 tick；不同入口场景重叠 128 tick。等待中保存及重新加载后仍按同一顺序完成。独立出口场景中，两车正常停站，慢车无额外出口等待。

这些普通停站场景在旧实现也可能正确运行，作为防回归覆盖；不能把它们冒充玩家此前每一次提前开出的历史过程都已复现。本轮确实复现的原生行驶差异是上述“有侧线却停在正线”，以及存档中站后共同路径被误判为独立。

## 原问题存档重放的边界

修复后用固定副本重放 6,000 tick，读取地图 15 个区域配置，车辆位置索引及路签索引异常为零。238／240 的后续共同出口已能正确识别。

但是，保存时 240 已越过可进入相关侧线的岔口，并持有合法前进预留；本轮没有非法清空 PBS、把车辆倒回或强行改道。该次原样重放的行驶先后未被回滚。因此不能声称它会从这一保存位置立即回到侧线、让 238 先行。改进适用于仍有合法候选进路的重新评估；原生预留安全继续优先。

## 验证及性能

- Windows x64 Release 编译成功，456 项测试、43,314 条断言通过。
- 两种制动方式、两种入口配置共 128 次原生行驶／重载通过，包括 32 次新增停站场景；同时保留连续快车、未知路径、改道、交叉、前／尾检测及满线远近腾位回归。
- 既有复合入口、普通／全站台／混合、桥头及跨公司登记的 42 次行驶／重载通过，总计 170 次。
- 最终构建的服务器和两个本机客户端加载“快车停站、慢车等待”存档，比较共同 tick 的车辆、随机、路签、预留及校验状态。准确结果记录于包内 `validation/network-result.json`；不据短时测试宣称所有地图永久无不同步风险。
- 四项菜单在普通与高级模式均核对，旧条件仍可显示和执行。
- 继续使用既有有界拓扑预算；没有全图列车扫描、长期拓扑缓存或并发修改模拟状态。新增加的调度读取同样有界，不执行预测命令。

调度条件或子计划返回方向无法唯一确认时保留未知；超出预算的复杂站场不能承诺全部可预测，也不为满足优先级强行改写原生路径。
