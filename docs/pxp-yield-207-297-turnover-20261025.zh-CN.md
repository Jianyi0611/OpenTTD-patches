## 294～297 的堵塞与修复

原存档中，294、295、296 已分别占用三条待避股道，并保存了等待 297 的依赖；295、296 占的是 297 正常停站可用的两条站台。297 当时零速等待。不能仅凭“来自不同线路”就认定四车完全独立：297 的两个合法站台选择均被占用，未来进路也尚未唯一确定。

确认并修复了两处疏解失败：

- 邻近区域内、数百格外且没有已确认依赖的列车，其未知进路会否决必要的站台腾空。`TurnoverCost` 现在区分未确认的远处候选、局部优先车和已有有效依赖；局部未知关系与有效依赖继续保守处理。
- 在实际出口回调中，先做的可选路径预测可能耗尽预算，使出口无法重现先前已证明的站台腾位方案。`ExecuteAutoYield` 对确实停在已认领站台、且确有站台请求的情况先完成有界疏解计算，并在本次调用内复用结果。没有设置永久放行标志。

同时建立了可重复失败的单元场景：快车有两条合法停站支线，旁边绕行正线无法到达当前车站。原实现仍把该正线视为快车追踪进路。`MainTargetProvenUnreachable` 与 `FollowingThreat` 现在只在完整证明正线无法服务当前车站时，要求另有真实共享轨道证明才能建立追踪关系。未知、循环、预算不足都不能证明独立。几何正线信息仍供正常站台容量疏解使用，避免把站台请求一起丢掉。

## 满线腾位与 PBS 区间修复

正常满线策略先考虑最高设计速度且通过安全检查的占用列车；到达慢车按沿共同优先快车实际路径的距离排序。最近慢车不比所有占用车慢时，保留满线正线例外；全等速情况保留 32 格近距离保护和安全的停队疏解。停站、装卸、连挂和所需站台的既有规则优先。

新增真实行驶测试还发现：160 列车虽已通过 PXP 清除点，却仍占用清除点后很长的原生 PBS 区间，200 快车因此在信号前停车。此前只比较到清除点的时间低估了阻挡风险。

`ProveTurnoverReleasePath`、`EarliestTurnoverConflict` 和 `TurnoverCost` 现检查：

1. 出发列车的真实车体、唯一合法出线方向、清除点和后续原生信号。
2. 后续安全停车位置必须让整个车尾越过相关清除边界；信号太近就继续检查下一段。
3. 优先车各合法前进分支最早可能到达共享轨道／交叉资源的位置；不是地图直线距离。
4. 用整数时间估算、列车长度与起步余量比较风险；不完整证明不得授予可选腾位例外。
5. 请求者自己的临时正线预约不能循环否决让它转入侧线的联合方案。仅在只读假设中折扣该列车自己的预约；车体、其他车辆预约和原生 PBS 实际执行均继续有效。

所有查询共用每次 1024 节点总预算；部分可选子查询重新分配额度，并复用本次调用内的结果。没有放宽总预算，没有多线程修改模拟状态，没有修改原生寻路算法或用惩罚代替停车。实际出发始终要求原生 PBS 合法预留。

真实双侧线测试采用未修改规格的原版 112 / 120 / 144 / 160 / 200 列车。覆盖 160 先安全腾位、最近慢车进线停车、200 通过时慢车保持零速、恢复出线、两种制动、等待中保存重载，以及长编组（长度 160）。还保留长 PBS 区间、快车太近时禁止强行腾位的反例。相邻慢车只有在本体和合法预约确实允许腾位时才可交换；不存在安全腾位窗口时允许原有满线例外，不能为满足排序强行放车。

生产逻辑集中在 `src/tracerestrict_overtaking.cpp`，测试在 `src/tests/train_decouple.cpp`、`regression/automatic_yield`。没有增加存档字段或新存档版本。缓存仅在一次只读判断内有效，轨道、命令与 PBS 状态变化后重新读取。控制菜单仍只有接近检测、正线控制、待避股道出口、车尾清除点四项。

最终编译及基础测试：**466 项测试、43,910 条断言通过**。真实行驶矩阵 **200 次**，既有复杂入口／站台／桥上登记回归 **42 次**通过。断言检查了实际进线、零速等待、快车通过时持续停车、车尾出清、恢复和认领释放，未以单一状态标志替代真实行驶。
