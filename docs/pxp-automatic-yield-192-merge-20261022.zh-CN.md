# 192 类合流前提前待避修复

## 原因

问题存档中的 192 号从另一条来线驶入，其最近的正线标记位于下方线路；实际寻路候选却会先借用 193 号所在的上方正线，再折回普通侧线。
旧判断一直使用最近的正线标记，直到车头已经合流才识别同一正线上的快车，造成先占正线、再待避以及快车减速。
此外，预留终点前方能到达一个侧线出口，原先被当作“不必重选”的理由；这并不能证明当前预留本身已经进入侧线。

## 改动

- 对当前正线信号候选使用其确切正线标记进行距离及优先级判断；先做原有最近正线查询，只有候选不同才做第二次有上限的只读证明。
- 禁止用原来线上的空正线为借用快车来线开脱。有已证明可用侧线时，让原有 PBS/YAPF 重选可用路线。
- 周期复核保留现有 8 tick 按车辆编号分摊的频率；若新出现的快车使预留绕到另一条来线，即使终点之后仍有侧线，也在尚未过合流点时允许重新预留。
- 满线腾位仍使用侧线出口也能重现的公共参与者分类，不根据一个尚未采用的候选虚构腾位等待。
- 已有侧线认领、办客、连接、换向、强制通行、实际占用和 PBS 安全保护保留。

没有修改寻路算法、轨道选择算法、命令协议或存档字段。所有新增数据只存在于单次模拟判断，仍受原有节点预算限制，不依赖墙钟、客户端、随机数或持久缓存。

## 验证

构造与问题机制相同的两来线场景：候选有多个后续分岔，普通侧线带惩罚值，慢车先产生跨线预留，随后快车进入检测范围。

| 同一初始场景 | 借用快车来线 | 进入原来线侧线 | 正常停车待避 | 快车检测区间最低速度 |
| --- | --- | --- | --- | --- |
| 修改前 | 是 | 否 | 否 | 0 |
| 修改后 | 否 | 是 | 是 | 200（最高速度） |

- 修复后的同一测试存档重载：正常进侧线、等待快车车尾出清并离开。
- 新增候选正线回归含空侧线与已满侧线分支。
- 全部 428 项测试、17195 个断言通过。
- 普通/长预留、来线互换、三种领签方式、分出口及重载，共 28 次既有受控场景复测通过。
- 荒山上行修复一并保留，问题存档 8000 tick 重放，97、159、38、85、81 均正常出清。
- 最终本机三端结果附 validation/network-final.log。只覆盖已测试场景，不能据此断言所有联机操作均无风险。

## 使用边界

原始 192 存档中车头已经过合流点。本修复预防尚未过岔的后续情况，不把已经占线的车辆移回另一条轨道，不撤销其他车的保护预留。
快车需按所选领签时机进入检测范围后才能参与判断；车尾领签或检测点设置太靠后时，不能倒推尚未登记的列车。
只有安全可用的替代股道存在时才提前分流；满线、岔区已被占用、人工限制或列车已过岔时，继续遵守实际 PBS 和既有腾位规则。
