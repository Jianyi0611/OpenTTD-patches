# 自动待避通用拓扑工程审查与验证

## 阶段 A：修改前审查

基线为 px-patch / d5ec2f02，叠加现有未提交修复。原文件、补丁、状态和问题存档已独立备份至 `D:\gpt\tools\yield-topology-20261023`。以下位置按修改前源码计。

调用链：原生 PBS/YAPF 临时路签事务 → tracerestrict.cpp 指令执行 → ExecuteAutoYield / EvaluateAutoYield；车头、车尾由 TrainControllerTraceRestrictFrontEvaluation 及对应车尾回调触发。AutoYieldGameTick 负责周期重评估。车辆删除走原生槽位清理，连挂沿用原生身份迁移。读档恢复现有普通及内部路签，当前自动待避存档版本为 10。

### 已确认问题

1. `src/tracerestrict_overtaking.cpp:870` FollowingClearanceDistances 的唯一后续路线分支未比较两车清除点 ID，不同出口距离可能被当成同一汇合点距离。
2. 同文件 `FollowingThreat:905`：未知距离 UINT_MAX 可能通过“大于慢车距离”的判断。
3. 同文件 `MustWait:1020`：既不能证明独立也不能证明反向，即被判为需要等待；不符合“不确定不能视为确定冲突”。
4. 同文件 `NeedsSiding:960`：稀缺股道分配首先按最低速度，实际追近距离仅是后续排序因素。
5. 同文件 `AutoYieldGameTick:1803`：已实际进入检测区的成员主要依赖车尾清除、手动取消、删除或回库释放；修改路线绕过清除点后存在残留风险。

### 需要进一步测试的风险

- FreeLane 的进入、容纳及到清除点证明尚不等于到当前调度目的地的证明；多出口应避免引向错误线路。
- FreeParallelMain 证明有另一条正线，不必然证明其后方无共同瓶颈。
- ClosePassenger / 等速腾位的距离参照应保持一致，不能混用不同清除点。
- 共享入口、站台工作、满载腾位及闭环逃逸相互影响，修改未知路线策略必须回归验证这些功能。
- 多区域成员身份本身可以合法重叠，不能简单删除“重复”成员；应区分真实占用与失效意图。

### 已保留的安全结构

使用原生有向轨道跟随和 PBS；读取物理车体及精确轨道预留，包括非路签成员、其他公司和倒车车辆。道岔停车长度不包含重叠冲突区。临时槽位随原生预留失败回滚。查询缓存仅在一次评估中有效，按游戏状态确定性执行，不使用本地时间或随机决策。

搜索有界：单次路线 256、评估总量 1024，当前活动区域成员/正线/检测点/待避线各有 16 的限制。超过范围不是已支持的无限拓扑；必须明确保留限制。

## 阶段 B：实施方案

1. 修复公共出口证明，建立明确的已知冲突、独立、未知分类；未知不增设自动等待，安全仍交由原生 PBS。
2. 对股道、出口和当前目标的关系增加正向证明；无证明不得封锁所有原有可行路线。
3. 稀缺股道结合已证明的追近风险和可达性排序，保留站台工作和合法腾位保护。
4. 增加有界状态有效性检查，仅在证明离区后释放；车体仍占用、查询超限均不能冒充离区。
5. 使用现有调试设施记录原因，默认关闭，不为日志额外寻路。
6. 增加针对缺陷、方向变换、随机种子、状态变化的测试；完整回归、原生运行、读档及本机联机验证后记录实际结果。

## 阶段 C–E：本轮实现

修改生产代码仅涉及 `src/tracerestrict_overtaking.cpp`，测试在 `src/tests/train_decouple.cpp`。工作区原有的 PBS 修改另有先前备份，本轮没有改写原生寻路算法。

| 问题 | 本轮处理 |
|---|---|
| 不同出口距离被当成同一汇合点距离 | FollowingClearanceDistances、ClosePassenger、EqualSpeedTurnover 对齐实际清除点 ID |
| 未知距离 UINT_MAX 被当成远处跟车 | FollowingThreat 仅使用已知、同参照的距离 |
| 无法证明独立即要求等待 | ClassifyYieldConflict 区分未知、独立、共享有向资源；通过已证明的有向路径前段或共同出口确认冲突 |
| 远处快车一直占有优先权 | MustWait 在同一出口距离已知时增加整数行程估计，含车长和出清余量；保留近距离等速客车规则 |
| 只看最慢车 | 稀缺空股道先比较已证明的追近时间，再比较到控制点距离、速度及稳定车辆 ID；不能及时进入或长度不足的车不占名额 |
| 远车耗尽查询预算 | 优先解析当前车和高优先级车辆；证明结果只在本次评估缓存，保留原有总搜索上限 |
| 未知结果又被用来证明客车可以优先开出 | 客车出口优先需要完整判断；“未确认需要等待”不等于“确认可以拦住别人” |
| 多出口侧线可能绕向错误目标 | 有明确目的地时，FreeLane 要求候选清除点与目标预测一致；无法确认则不据此禁止原本正线路径 |
| 预测越过尚未完成的车站目标 | 搜索正线控制点时不穿过当前必须到达的车站、路点或车辆段来猜测下一条调度 |
| 漏过清除回调或从入口倒退出区 | ProvenOutsideArea 对整列车逐段验证向外越过边界后清理；仍在边界、存在不明分支、回路或超出预算时不提前释放 |
| 日志不足 | 使用现有 `yapf` 调试级别 6/7 输出区域、车辆、信号、方向、目标、冲突类别、车位排除原因、权限、结果及清理原因 |

新增查询缓存不跨模拟步、不写存档。生命周期补查每个区域每 64 步轮转检查一辆已登记车辆，避免每步扫描全地图。释放的是路签状态，不强制清空轨道预留。

### 策略变化需要注意

这次请求明确要求“不确定不视为冲突”和“不简单选最慢车”，因此修订了以前对应的旧测试预期。仍保留其调度、路签、索引及随机数不被查询修改的检查。车尾保护测试改为实际放置尚未出清的车尾，而非只保留一个与物理位置不符的成员记录。

站台作业、连挂作业是否完成由原生车辆状态继续控制；取消额外待避等待不等于强制列车提前结束装卸或穿过红灯。普通腾位是否可行仍独立验证，不以“未设置等待标志”冒充“已经安全腾位”。

### 性能

相同问题存档分别使用修改前后源码编译的测试程序，跳过 64 步预热，统计 1,000 步；按旧/新/新/旧顺序执行。旧版 4,944 / 4,983 毫秒，修改后 4,988 / 4,995 毫秒，均值增加约 0.56%；见 `validation/benchmark.log`。只有两次样本，包含不同运行决策造成的后续状态差异，不是帧数提升的证据，也不能推算所有存档的开销。

长时间测试可能与联机测试并行执行，其耗时不能用于前后性能比较。默认关闭诊断；启用 `-d yapf=7` 会产生大量日志，只用于排查。

未增加存档字段、版本或命令。沿用现有普通/内部路签以及原生预留事务；读档副本成功完成后续运行。排序使用整数和车辆 ID，缓存只在当前评估内使用，清理轮次来自游戏模拟步。

## 尚未解决或需要明确的边界

- 当前区域仍有限额：16 个活动成员、16 个正线标记、16 个待避车位和 16 个接近点；更大区域没有在本轮实现。搜索超限时回退到普通信号行为，不保证安排出最优待避顺序。
- 追近时间是按检测最高速度计算的相对估计，没有完整模拟加速度、坡道、装卸耗时或所有未来条件调度。因此是风险排序改进，不是全局最优调度证明。
- 正向目标预测无法可靠解析的复杂多出口，可能放弃本次自动分流，而不是冒险阻止全部合法路线。
- 整列车离区证明不完整时保留成员；删除清除点、复杂回路、桥隧或跨区域交织仍可能需要重新配置或手动取消失效路签。没有证明所有异常状态都能自动清理。
- 未证明任意多区域闭环、无限连续快车到达下的公平性，也没有“所有有效铁路绝不死锁”的保证。
- 本轮没有发布到 GitHub；工作区原有未提交内容仍保留。Windows 包与测试日志在 dist。

本轮完成了上述通用修复和可复现实测；“全拓扑兼容、所有相关问题彻底消除”仍未达到全面验收条件。
